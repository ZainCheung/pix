# Pix wire protocol v1

This directory documents the plaintext application schema encoded and decoded
by `pix-wire`. These messages are never sent directly over TCP or the relay.
The secure-channel layer authenticates and encrypts each encoded message first.

## Envelope

Client requests contain:

- `protocol`: integer major version, exactly `1`;
- `request_id`: connection-scoped unsigned integer;
- `type`: dotted operation name;
- operation-specific fields.

Server messages contain:

- `protocol`: integer major version, exactly `1`;
- optional `request_id` when acknowledging or answering a request;
- `type`: dotted event name;
- event-specific fields.

Unknown enum variants and incompatible major versions fail closed. Request IDs
deduplicate only within the current authenticated connection.

## Requests

`host.snapshot`, `host.defaults`, `workspace.list`, `session.list`, `session.create`,
`session.attach`, `session.history.request`, `session.rename`, `session.release`, `session.prompt`,
`session.steer`, `session.follow_up`, `session.abort`, `session.compact`,
`model.list`, `model.set`, `thinking.set`, `extension_ui.respond`,

## Events

`request.ack`, `host.snapshot`, `host.defaults`, `workspace.list`, `workspace.changed`,
`session.list`, `session.snapshot`, `session.state`, `session.queue`,
`session.history.page`,
`user.message`, `assistant.delta`, `assistant.message`, `tool.start`, `tool.update`,

## Capability negotiation

The protocol major stays `1`; additive extensions are negotiated per connection.

- The client declares capabilities on its `host.snapshot` request:
  `{"type":"host.snapshot","capabilities":["commands.v1","queue.v1", ...]}`.
  Capability strings match `[a-z0-9._-]{1,24}`; at most 16 may be declared.
  Unknown capabilities are accepted and ignored.
- The host advertises what it can honor in the `host.snapshot` response:
  `{"host":{...},"capabilities":["commands.v1","queue.v1","attachments.v1","usage.v1","thinking_levels.v1","session_metadata.v1","image_refs.v1","session_history.v1","history_items.v1","history_presentation.v1"]}`.
- A connection's usable extension set is the intersection. The host omits every
  gated field and never emits a gated event until the client declares the
  matching capability. An old host ignores the unknown request field and
  responds without `capabilities`, so a new client degrades to the base v1
  feature set instead of failing.

Current capabilities:

| Capability | Unlocks |
| --- | --- |
| `commands.v1` | `commands` array in `session.snapshot` |
| `queue.v1` | `queue` in `session.snapshot` and `session.queue` events |
| `attachments.v1` | `attachment.*` requests and prompt/steer/follow-up `attachments` |
| `usage.v1` | `usage` object in `session.snapshot` |
| `thinking_levels.v1` | authoritative per-model `thinking_levels` in snapshots |
| `session_metadata.v1` | asynchronous `session.metadata` enrichment event |
| `image_refs.v1` | `imageRef` history entries and lazy `image.get` reads |
| `session_history.v1` | bounded recent `session.snapshot` history plus `session.history.request` pages |
| `history_items.v1` | source-indexed `history_items` with bounded placeholders for oversized/unrenderable messages |
| `history_presentation.v1` | semantic tail anchors and active/settled Turn presentation state in `history.presentation` |

## Session history pagination

`session.snapshot` is deliberately not an export of the complete Pi session
when `session_history.v1` is negotiated. It contains the session metadata and
the newest byte-bounded message window, followed by:

```json
{
  "history": {
    "start_index": 91,
    "has_more": true,
    "cursor": "opaque-cursor",
    "revision": 141
  }
}
```

`start_index` is the message index of the first item in `messages`. `revision`
identifies the history boundary captured for this view; it is opaque and is
stable across pages even while newer live events arrive. `cursor` is returned
unchanged by the host and must not be interpreted by clients. The initial
window is at most 50 messages and targets 512 KiB of encoded message content,
leaving room below the 1 MiB encrypted-frame limit. A single message that
cannot fit in a frame is represented by a placeholder when `history_items.v1`
is negotiated; a legacy `messages` request retains the original bounded-error
behavior. A placeholder contains only a role, semantic preview (at most 32
KiB UTF-8), original byte count, truncation flag, and optional content
reference. It is not a raw JSON fragment.

When `history_items.v1` is negotiated, `session.snapshot` and
`session.history.page` use `history_items` instead of `messages`. Items are
contiguous and carry their absolute source index:

```json
{"kind":"message","index":91,"message":{"role":"user","content":"…"}}
{"kind":"placeholder","index":92,"role":"assistant","preview":"…","original_bytes":7340032,"truncated":true}
```

The host retains an in-memory, content-free index and selects pages from the
last committed complete JSONL record. A partial trailing record is excluded.
The modern opaque cursor binds the exclusive `before_index` to that record's
byte offset, a history epoch, and a boundary fingerprint. Appends after the
boundary do not change the cursor; a rewrite or truncation invalidates it and
the client must attach again. Legacy v1 cursors are accepted through the
compatibility reader path.

When the reader reaches the beginning of the loaded timeline it requests an
older page:

```text
session.history.request {
  session_id,
  before: cursor,
  limit: 50
}
```

The response is a flattened `session.history.page` event:

```json
{
  "type": "session.history.page",
  "session_id": "…",
  "messages": [],
  "start_index": 41,
  "has_more": true,
  "next_cursor": "opaque-cursor",
  "revision": 141
}
```

Pages preserve the original revision boundary and are selected by both a
maximum message count (50) and a 512 KiB target. The host reads the native Pi
JSONL source incrementally, so opening a long-running session does not ask Pi
to serialize the complete in-memory `messages` array. History pages and live
`user.message`/assistant/tool events are separate streams; clients prepend a
page by `start_index` and continue appending live events.

### Semantic tail presentation

With `history_presentation.v1`, `history.presentation` is always present on a
history-capable snapshot, including when the history file is temporarily
unavailable. It contains:

- `turn_state`: `active`, `completed`, `failed`, `aborted`, or `compacted`;
- `user_anchor`: the last user message source index and an optional bounded
  preview when it is outside the initial page;
- `terminal_anchor`: the last non-error assistant result that has no pending
  tool call, with the same preview rule;
- `process`: counts of omitted thought/tool/error records and an `omitted`
  flag; and
- optional `error_summary`.

Clients should use the anchors to guarantee the final user/assistant exchange
is visible on first open. For idle/sleeping sessions, process rows from a
settled Turn may be collapsed by default. For an active Turn, the current
tool/thought process remains expanded until the host reports a terminal state.

## Slash commands

`session.snapshot` may carry `commands`, one entry per Pi slash command that is
invocable through a prompt. Each entry contains only `name`, optional
`description`, `source` (`extension`, `prompt`, or `skill`), and optional
`scope` (`user`, `project`, or `temporary`). Pi's `sourceInfo` paths and
package metadata never cross the host boundary. Commands are invoked by
sending their `/name text` form as ordinary prompt content; Pi rejects
extension commands inside `session.steer` and `session.follow_up`, so clients
must route extension commands through `session.prompt`.

When `session_metadata.v1` is declared, `commands.v1`, `usage.v1`, and
`thinking_levels.v1` are returned after the base `session.snapshot` in one
unsolicited `session.metadata` event. The host bounds each Pi probe and may
omit an individual field when Pi does not answer in time. A client must render
the snapshot without waiting for this event.

## Queue visibility

While a session runs, Pi reports queued messages. The host caches the latest
queue in the runtime (never in durable storage) and exposes it two ways:
`session.queue` events mirroring Pi's live `queue_update`, and the `queue`
object (`steering` and `follow_up` string arrays) inside every
`session.snapshot`. The cache is ephemeral: it dies with the Pi runtime and
reconnects recover it without a Pi round trip.

## TUI snapshot cursor

The additive `inflight_assistant` and `through_sequence` fields may be present
when the session is owned by the optional Pi TUI bridge. `inflight_assistant`
contains the current partial assistant message, if any. `through_sequence`
identifies the last bridge event already represented by the snapshot; clients
must render the snapshot first and then apply later live events. Native RPC
snapshots omit both fields, and older clients may safely ignore them.

## Attachment transfer (images)

Images ride the existing encrypted frames in bounded chunks instead of
raising frame limits:

```text
attachment.begin   {session_id, attachment_id, mime_type, size}
attachment.chunk   {attachment_id, data}   # base64, each ≤ 512 KiB decoded-string limit
attachment.finish  {attachment_id}
session.prompt     {session_id, content, attachments: [attachment_id]}
```

Limits, enforced at both the wire and the host:

- mime types: `image/png`, `image/jpeg`, `image/webp`, `image/gif`;
- one attachment: 1..=4 MiB decoded bytes;
- at most 9 pending uploads and 9 references per request, per connection;
- uploads idle for 10 minutes are dropped, as are all uploads when the
  connection closes;
- the host rejects a prompt whose assembled base64 images exceed 12 MiB,
  keeping the Pi RPC record below its 16 MiB ceiling;
- uploads are single-use: the accepting prompt consumes them.

The host assembles chunks in bounded memory, atomically persists the image
under its configuration directory, and forwards the vision bytes to Pi as one
`images` array on the RPC prompt. The agent-compatible path is appended to the
prompt as host-local text. Asset files never enter the relay.

## Historical image references

With `image_refs.v1`, Pi `ImageContent` entries in a session snapshot are
externalized to:

```json
{"type":"imageRef","id":"sha256:<64 hex>","mimeType":"image/jpeg","size":135896,"pixelWidth":1179,"pixelHeight":1452}
```

`pixelWidth` and `pixelHeight` are optional original-image dimensions. They
allow a client to reserve the final single-image aspect ratio before fetching
the lazy vision bytes; multi-image galleries still use fixed square cells.

The host derives the asset from the Pi base64, so Pi JSONL remains the source
of truth even if the derived cache is deleted. A client requests a bounded
range with:

```text
image.get   {session_id, image_ref, offset, limit}
```

and receives `image.chunk` (`data` is base64, `eof` marks the final range).
The maximum decoded range is 512 KiB. Clients should cache these ranges locally
and request them only when an image becomes visible.

## `host.defaults`

`host.defaults` reads Pi's persisted model selection and model catalog without
starting a session runtime. The response is scoped to the authenticated host
connection and contains only non-secret model metadata:

```json
{
  "model": {"provider": "opencode-go", "id": "deepseek-v4-flash", "name": "DeepSeek V4 Flash", "reasoning": true},
  "models": [],
  "thinking_level": "high"
}
```

When Pi has not persisted a selection, `model` and `thinking_level` may be
omitted/null and `models` may be empty. Pix never substitutes a product or
model name for an empty host response.

Session/model summaries may include an optional `input` array copied from Pi's
model metadata (for example `["text", "image"]`). Clients should only
offer image composition when the active model advertises `image`; an omitted
array means that the host cannot confirm image support.

## `host.snapshot` relay access

The `host.snapshot` event may include an optional `relay` object:

```json
{"relay": {"url": "wss://relay.example.com", "channel_secret": "base64url"}}
```

It is present only when the host has an active relay endpoint configured and
identifies the requesting device's durable rendezvous channel. The secret is
delivered exclusively inside the authenticated encrypted channel and must be
stored by clients with the same protection as host trust material. Clients
without relay support ignore the field.

## `session.list` limit

`session.list` may include an optional `limit` integer. When present, the host
returns at most that many sessions, newest first, and never more than 200.
Omitted `limit` keeps the previous unbounded list. The response shape is
unchanged. Clients without this field continue to work.

Home does not use a `home.snapshot` aggregate. Workspace rows load first;
session summaries load when a workspace expands.

## Relay transport

The relay carries the same length-prefixed encrypted records as direct TCP;
it terminates WebSockets, never the Pix secure channel.

Derivations (implemented once in `pix-wire`, fixture
`protocol/fixtures/v1/relay-channel.json`):

- `channel_id = hex(Blake2s256("Pix relay channel v1" || secret))`;
- `join_proof(role) = hex(Blake2s256("Pix relay join v1" || role || secret))`
  with `role` being the ASCII string `host` or `client`.

Join request: `GET {relay}/v1/channel/{channel_id}` upgrading to WebSocket
with headers `X-Pix-Protocol: 1`, `X-Pix-Role: host|client`, and
`X-Pix-Join-Proof`. The relay pins the first proof per role and role
cardinality is one connection; a newer valid join supersedes the older one
(close 4008).

Messages:

- binary: exactly one length-prefixed encrypted record (at most
  1 MiB + 4 bytes), forwarded verbatim to the opposite role, dropped without
  queueing when the peer is absent;
- text from relay to endpoint: `{"type":"peer_joined"}` and
  `{"type":"peer_left"}`;
- text from endpoint to relay: protocol violation, connection closed.

The QR payload for remote pairing is
`pix://pair?v=1&relay={ws-url}&secret={channel_secret}&fp={host_fingerprint}`
with a percent-encoded relay URL. The same rendezvous can be entered by
typing an eight-character Crockford join code `XXXX-XXXX` plus the relay
URL; the channel secret is derived in `pix-wire` as
`Blake2s256("Pix remote join v1" || normalized_code || 0x00 || relay_url)`.
The pairing channel is single-use and expires two minutes after
presentation; the Noise XX flow, token, and six-digit confirmation are
identical to LAN pairing.

## Resource limits

- encrypted frame: 1 MiB;
- any decoded string: 512 KiB;
- pending requests per authenticated connection: 128;
- outer stream prefix: unsigned 32-bit length in network byte order;
- relay WebSocket message: one encrypted frame plus its 4-byte prefix.

Fixtures under `protocol/fixtures/v1` are canonical Rust-generated byte
sequences and must be decoded unchanged by Swift tests. The set includes one
file per request and event type, plus pairing, confirmation, fingerprint,
expiry, and maximum-frame rejection fixtures. Generate them with
`cargo run -p pix-wire --example generate_fixtures`.
